FPL forecasting

Predict the next gameweek from completed data.

The pipeline requires season-wrapped completed snapshots, stops every feature at the as-of gameweek, and compares ridge regression with recent-form baselines in time order.

Read the guideInspect the protocol

The time boundary

The difficult part is not fitting a regressor. It is proving that every input existed before the outcome and that every reported prediction came from a later gameweek.

1

Strict inputs

Unwrapped, empty, duplicate, gapped, cross-season, malformed, and low-coverage snapshots fail before feature construction.

2

As-of features

Latest form, rolling windows, and season totals stop at gameweek t; the target comes from completed t+1.

3

Bound deployment

The final artifact records its season, feature schema, protocol configuration, and training boundary.

Leak controls

  • No empty future gameweek becomes a zero label
  • No player absence is silently converted to zero
  • No identifier or target enters the feature matrix
  • No test gameweek precedes training data
  • No executable pickle artifact is loaded
  • No stored batch is served under a different model identity

Included

Focused tests cover the data contract, future-invariance, boundary guards, chronological splits, ranking metrics, end-to-end evaluation, CLI flow, and artifact round trips.

No source records or fitted model ship. A compact historical aggregate evaluation and source manifest are retained. Run fpl-forecast synthetic --season 2025-26 for a deterministic example, then replace it with explicitly wrapped completed-gameweek files.

The service is deliberately narrow. It opens one already prepared DuckDB database read-only, binds stored results to the exact model ID, and has no HTTP route for training, uploads, registration, or writes.

The generated report is a single local HTML file with no external scripts, fonts, trackers, or network calls.
